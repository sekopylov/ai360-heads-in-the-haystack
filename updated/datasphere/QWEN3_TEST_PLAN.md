## 1. Обзор длины и позиции needle

```bash
.venv-datasphere/bin/python datasphere/cli.py project job execute \
  -p bt1u5v72b71eesdhp9k5 -c datasphere/qwen3-survey.yaml
```

3 исходных корпуса (`part1/2/3`), каждый со своим needle-вопросом, ×
длины 4000/8000/16000/24000 × глубины 15/45/75 = **36 генераций**.
Новых окон и дополнительных повторов нет. Данные и алгоритм подготовки контекста
не изменены. Результаты и общий рейтинг находятся в `qwen3-survey/detection/`.
Длина задаётся конструктору haystack, это не точное число токенов полного chat prompt.
Проверяем, сохраняется ли извлечение при удлинении текста и перемещении ответа
в начало/середину/конец, а также повторяется ли лидерство голов 22–23 и 13–15.
Индексы голов и слоёв с нуля. Рейтинг заранее не зафиксирован.

Проверить до основного теста:

- `runtime.json`: CUDA доступна, Tesla T4; в логах источник модели local и CUDA-устройства.
- `detection/run.json`: `complete=true`, `completed_cases=36`.
- Для каждой пары длина/глубина: ROUGE recall, доля `score > 50`,
  число остановок по EOS и по лимиту, длины генерации и время.
- Незавершённое thinking отделять от неверного завершённого ответа;
  также учитывать обрезанные ответы, у которых `</think>` уже есть, но EOS нет.
- `head_scores.json`: значения 0..1; рейтинг усредняет **только случаи с ROUGE > 50**.
  Размер истории поэтому может быть меньше 36, а пропуски — не нулевые оценки.
  Нельзя объявлять головы устойчивыми по одному общему среднему.

При заметном числе обрезанных baseline-ответов сначала повторить нужные клетки
с `--max-new-tokens 4096` и другим `--output-root`, затем выбрать единый лимит
для всех условий основного теста. Не смешивать эти результаты с исходным лимитом.
На T4 прошли 1000 и первые три 4000 случая; 8000 на обычном SDPA вызвали OOM.
Новый memory-efficient backend прошёл отдельную GPU-проверку 24000 на depth45.
Обзорный запуск также проверяет память до дорогого masking sweep.

## 2. Парное маскирование на отдельном корпусе

```bash
.venv-datasphere/bin/python datasphere/cli.py project job execute \
  -p bt1u5v72b71eesdhp9k5 -c datasphere/qwen3-full.yaml
```

Этот запуск строит **свой** рейтинг на 18 detection-кейсах:
3 вопроса × длины 4000/8000 × глубины 10/50/90.
Он не читает прежний smoke или результаты survey.
Затем использует другой корпус, Paul Graham, и другой вопрос (San Francisco).

| Параметр | Значение |
|---|---|
| Длины / глубины | 4000, 8000 / 10%, 50%, 90% |
| Контекстные seeds | 42, 43, 44 |
| Условия | baseline; top-1/2/4/8; random-1/2/4/8 |
| Random-повторы | 3, head seeds 42/43/44 |
| Лимит | 2048 новых токенов, включая thinking |
| Retrieval-score | multiset, только финальный ответ |
| Маскирование | legacy_uniform, весь decode, включая thinking; prefill не изменён |

18 baseline + 72 top-k + 216 random-k = **306 masking-генераций**;
с detection всего **324**. Среди 1152 голов маленькие k проверяют, дают ли
несколько лидеров эффект, а увеличение k — растёт ли он вместе с вмешательством.
Каждая пара baseline/top/random должна иметь одинаковый `prompt_sha256`.
Random по текущей семантике исключает top-k и выбирается заново для каждой клетки;
фактические наборы сохраняются как `blocked_heads`. Это контроль не из всех голов.

Основной вопрос анализа: насколько падение ROUGE относительно **своего baseline**
у top-k больше падения у random-k на той же длине/глубине/контексте?
Показать парные разности, разброс random-повторов и результаты по длине/глубине,
а не только средний столбик. Отдельно показать частоту обрезанного thinking
и длительность генерации: маскирование может менять и их.
ROUGE здесь — recall, не F1; 100 не доказывает отсутствие лишних слов.

## Ограничения и дальнейшие проверки

- Это несколько часов GPU, не smoke. Даже при средней минуте на генерацию
  основной запуск займёт около 5.4 часа плюс установка, загрузки модели и прочие накладные расходы.
  Это арифметический ориентир, не измеренный прогноз для длинных контекстов.
- 3 detection-вопроса и 1 masking-вопрос ограничивают обобщение. Три context seeds
  меняют порядок эссе, но не создают три независимых вопроса. Не выдавать сотни
  генераций за сотни независимых примеров.
- Этот тест не изолирует маскирование только финального ответа: вмешательство
  действует и на thinking. Гейтинг только оценки не меняет это.
- Если top-k отличается от random, следующий шаг — подтверждение на новых вопросах
  и отдельном запуске `zero_output`. Не смешивать его с `legacy_uniform`.
- Для устойчивости рейтинга сравнить оценки голов по трём исходным вопросам
  и по длинам/глубинам; один общий рейтинг не доказывает универсальность.
- Для проверки бюджета — парный повтор baseline и выбранных top/random с 4096,
  на тех же prompt и head seeds, в отдельном output-root.
- Полные attention traces не включены: для этого sweep они дороги и не нужны
  для рейтинга. Исходный текст, финальный ответ, token IDs и finish_reason сохраняются.
- Перед повтором любого конфига меняйте output-root и YAML outputs согласованно:
  старые файлы в локальной папке автоматически не удаляются.

Артефакты разделены: `datasphere-results/qwen3-survey` и
`datasphere-results/qwen3-full`. Эти конфиги не меняют существующие результаты.
