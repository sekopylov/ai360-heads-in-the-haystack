# Retrieval heads в Qwen3.5-0.8B: линейное внимание vs обычное

Порт кода [Retrieval_Head](https://github.com/nightdessert/Retrieval_Head) (Wu et al., 2024, [arXiv:2404.15574](https://arxiv.org/abs/2404.15574)) на гибридную Qwen3.5. Вопрос исследования: **есть ли поисковые (retrieval) головы среди голов линейного внимания (Gated DeltaNet), или они живут только в слоях полного softmax-внимания?**

## Модель

Qwen3.5-0.8B: 24 слоя, паттерн `LLLF` × 6.
- 18 слоёв Gated DeltaNet × 16 голов = **288 линейных голов**;
- 6 слоёв полного внимания (слои 3, 7, 11, 15, 19, 23) × 8 голов (GQA 8/2) = **48 полных голов**.

## Что сделано и чем отличается от кода авторов

1. **Детекция (`detect.py`).** Протокол как в статье: 3 иголки из `haystack_for_detect`, сетка длина × глубина, жадная генерация, засчитываются только ответы с ROUGE-1 recall > 50. Retrieval score головы = доля токенов иголки, которые голова «скопировала»: на шаге декодирования argmax внимания попадает внутрь иголки на токен, равный сгенерированному.
   - Для **полных голов** это обычная softmax-строка внимания.
   - Для **линейных голов** используется **точная неявная матрица внимания** gated delta rule. Из рекуррентности `S_t = α_t(I − β_t k_t k_tᵀ)S_{t−1} + β_t k_t v_tᵀ`, `o_t = S_tᵀ q_t` следует `o_t = Σ_i A[t,i]·v_i`, где `A[t,i] = β_i · k_iᵀ · N_{i+1}⋯N_t · q_t` и `N_j = α_j(I − β_j k_j k_jᵀ)`. Это не аппроксимация: выход головы восстанавливается из `A` и `v` точно. Строка `A` считается обратным проходом (чанками с треугольным решением), O(L·d) на голову. В отличие от softmax, `A` может быть отрицательной.
   - Сохраняются два варианта score: `attn` (argmax `A[t,i]`, прямой аналог статьи) и `contrib` (argmax `|A[t,i]|·‖v_i‖`, то есть размер вклада токена в выход головы). Если выводы по обоим вариантам совпадают, они устойчивы к выбору определения.
   - Вместо eager-внимания на каждом шаге делается **один** дополнительный прямой проход по `prompt + сгенерированное`. Запросные позиции те же, что у авторов (токен, подаваемый на каждом шаге декодирования).
2. **Абляция (`ablate.py`).** Голова «выключается» обнулением её выхода перед `out_proj`/`o_proj`. Операция одинакова для обоих типов голов, поэтому сравнение честное. Как у авторов, маска действует на шагах декодирования (`--scope decode`); `--scope all` выключает голову и на префилле. Эксперименты независимы по типу: top-K retrieval-голов **только линейных** против K **случайных линейных**, и то же для полных. Случайные головы берутся среди голов со score < 0.1, по нескольким сидам.
   - Отличие от авторов: они не обнуляли выход, а ставили логиты маскируемой головы в 0 (равномерное внимание). У линейных голов softmax-логитов нет, поэтому для сопоставимости используется обнуление.
3. **Графики (`plots.py`)** в стиле статьи:
   - `fig1_head_score_map.png` — карта retrieval score всех голов (слой × голова), строки полного внимания выделены;
   - `fig2_score_distribution.png` — доля голов со score ≥ x для линейных и полных голов и максимальный score по слоям;
   - `fig3_niah_K<k>.png` — NIAH-тепловые карты (как Fig. в статье): без маски / top-K / random-K, отдельно для линейных и полных;
   - `fig4_k_sweep.png` — средняя точность NIAH в зависимости от K (top vs random, linear vs full);
   - `summary.md` — таблицы с числами.

## Запуск

```bash
pip install -r requirements.txt   # нужна свежая transformers с поддержкой Qwen3.5
git clone https://github.com/nightdessert/Retrieval_Head ../Retrieval_Head   # только данные (haystack + эссе)

# 0) самопроверка: неявное внимание и хуки совпадают с реальными выходами голов, маска работает
python selftest.py --model_path Qwen/Qwen3.5-0.8B --haystack_root ../Retrieval_Head

# 1) детекция retrieval-голов (3 иголки × 20 длин × 10 глубин)
python detect.py --model_path Qwen/Qwen3.5-0.8B --haystack_root ../Retrieval_Head -s 1000 -e 16000

# 2) абляция: baseline + {linear, full} × {top, random×3 сида} × K
python ablate.py --model_path Qwen/Qwen3.5-0.8B --haystack_root ../Retrieval_Head \
    --head_score head_score/Qwen3.5-0.8B.json --kinds linear,full --ks 1,2,4,8,16 --seeds 0,1,2 -e 16000

# 3) графики и сводка
python plots.py --head_score head_score/Qwen3.5-0.8B.json --niah_dir results/niah --out figs
```

Или всё сразу: `bash run_all.sh`.

### Логи, прогресс и GPU

- Каждый скрипт пишет лог с таймстемпами в консоль и в `logs/<скрипт>_<имя>_<время>.log`. Строка пишется после каждого сэмпла:
  ```
  2026-10-12 01:14:03 | [detect 137/600 |  21.4%] elapsed 00:31:10 | ETA 01:54:20 (~03:08) | gpu 3.2G (peak 9.8G) | needle 0 len=13579 depth=44% rouge=100 used=True (14.2s, used 120/137) -> '...'
  ```
  Процент и ETA считаются по объёму работы (сумме длин контекстов), а не по числу сэмплов, поэтому длинные контексты в конце сетки не ломают прогноз. `ablate.py` ведёт один общий прогресс на весь свип (только по ещё не сделанным прогонам) и после каждого прогона пишет его средний score.
- `detect.py` каждые `--log_top_every` (по умолчанию 10) успешных сэмплов логирует текущий топ линейных и полных голов и сохраняет чекпоинт `head_score/<имя>.partial.json`.
- **Проверка GPU** при старте: версии torch/CUDA/transformers, имя и память GPU, тестовый матмул на устройстве, затем проверка, что все параметры модели лежат на `cuda`. Если CUDA недоступна, скрипт сразу завершается с ошибкой, а не считает тихо на CPU. Обойти это можно флагом `--allow_cpu`. `run_all.sh` дополнительно вызывает `nvidia-smi`.
- **Если процесс оборвался.** Необработанные исключения (включая CUDA OOM) пишутся в лог с полным traceback. Сигналы SIGTERM, SIGHUP (закрыли терминал или SSH) и SIGINT тоже попадают в лог отдельной строкой. Если лог просто обрывается без какой-либо записи, процесс убит через SIGKILL: OOM-killer, лимит контейнера или ноутбука, `kill -9`. В этом случае смотрите `dmesg -T | grep -i -E "killed process|out of memory"` и колонку `ram ... (free ...)` в строках прогресса.
- **Продолжение после обрыва.** Достаточно запустить ту же команду ещё раз:
  - `detect.py` пропускает сэмплы из `head_score/<имя>.samples.jsonl` и подхватывает их score из `.persample.jsonl`. Для старых прогонов, где этого файла ещё нет, score восстанавливаются из `.partial.json`. Флаг `--fresh` начинает с нуля.
  - `ablate.py` пропускает готовые прогоны и продолжает недописанный `.part`.
- **Скорость.** В каждой строке прогресса есть разбивка времени: `prefill Xs + N tok x Ys, capture Zs`. При старте в лог пишется, установлены ли `fla` и `causal_conv1d`. Без них Gated DeltaNet считается на медленном torch-фолбэке.
- Длинный прогон удобно запускать так: `nohup bash run_all.sh > run_all.out 2>&1 &`, а следить через `tail -f logs/*.log`.

Полезные опции:
- `--prompt_format raw` — без chat-шаблона, как для base-моделей (для `Qwen3.5-0.8B-Base`);
- `--head_score head_score/Qwen3.5-0.8B.contrib.json` в `ablate.py`/`plots.py` — ранжировать головы по варианту `contrib`;
- `--ks 1,2,4,8,16,32,48` — для полных голов K ≤ 48, для линейных можно идти до 288;
- `ablate.py` дописывает только недостающие прогоны, поэтому его можно прерывать и перезапускать.

Ресурсы: одной GPU на 24 ГБ хватает до ~32k токенов. Самая дорогая часть детекции — восстановление неявного внимания (18 слоёв, L/64 итераций на слой), это порядка секунды на сэмпл при 16k. Абляции дорогие по числу прогонов: при сетке 10×10 и K из 5 значений получается 1 + 2·5·(1+3) = 41 прогон по 100 сэмплов.

## Как читать результат

- **Retrieval-головы в линейном внимании есть**, если одновременно (а) у линейных голов есть заметные score (≥ 0.1, как порог статьи), стабильные между `attn` и `contrib`, и (б) маскирование top-K линейных голов роняет NIAH заметно сильнее, чем маскирование K случайных линейных голов.
- **Они только в полном внимании**, если линейные score около нуля, а top-K линейных ведёт себя как random-K, тогда как у полных голов разрыв top vs random большой.
- Промежуточный случай тоже содержательный. Например, линейные головы находят иголку (высокий `contrib`), но их выключение почти не вредит: копирование реально выполняют полные головы, а линейные дублируют.
